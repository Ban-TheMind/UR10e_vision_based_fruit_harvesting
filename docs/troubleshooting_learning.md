# 问题解决与学习复盘（内部）

这份文档服务于我们自己的复盘学习：原先设计（formulate）漏了什么、实际出现了什么、怎么处理、还有什么没有验证。对外项目介绍保留在 README；当前命令见 `operations.md`，验收顺序见 `test_plan.md`。

整理于 2026-10-10。依据项目 Git 修复历史、可检索测试对话及操作者补充；未取得完整现场晚间日志，因此不声称穷尽所有事件。**代码已修复、离线测试通过、真机已验收是三个不同结论。**

## 设计阶段遗漏及对应改进

| 原先未充分考虑的条件 | 实际影响 | 解决方法与后续原则 |
|---|---|---|
| 原仓库与现场操作系统、ROS 发行版不同 | Humble 配置不能直接保证 Foxy 行为兼容 | 单一 main 以 Foxy 为部署目标；历史 Humble 包排除编译；现场依赖及 Xacro 单独检查 |
| 夹爪型号和协议改变 | 原 OnRobot RG2 HTTP 接口不适用于 Robotiq 串口 | 保留 ROS 服务契约，后端换官方 SDK；宽度毫米与 force 原始编码明确区分 |
| ROS Python 与深度学习 Python 混用 | Foxy Python 3.8 与 VPP Python 3.10 依赖不能混装 | ROS 节点与 YOLO 子进程分离；协议离线测，真实推理另测 |
| 固定相机与腕部相机属于不同几何问题 | 原变换链及坐标符号可能错误 | 固定 Eye-to-Hand 矩阵与 UR base/base_link 的旋转明确分开；静止目标独立测量 |
| 机械臂工厂标定与相机外参被混为一谈 | 一份正确不能证明另一份正确 | 分别核对 UR 运动学哈希、相机安装外参、TCP/负载和工具模型 |
| 规划、控制器 active 和真实动作被混为成功 | 规划成功却完全不动 | 分开记录计划、action 结果和实测关节；有效速度为 0 时优先查运行链路 |
| 上层 launch 参数不一定被旧系统包转发 | headless 请求没有落实到硬件描述 | 展开后精确覆盖并校验参数；不修改系统包；核对 robot_description 实际值 |
| 速度缩放会改变执行时间 | 低速轨迹被名义时长监控误报超时 | scaled 控制器单独适配；这不会消除零速度或让机器人程序自动运行 |
| 多分支、不同构建目录与运行进程独立变化 | 修改被淹没、拉错分支、更新后仍跑旧服务 | main 单一维护；恢复统一 project；统一 install-project；更新、构建、重启、验收各自完成 |
| 无限重试及动作失败后继续 | 不知道流程何时结束或是否已抓住 | 有限循环、等待与检测；失败立即退出；超时标为状态未知 |
| 夹住后复位/提前张开、关节数组顺序差异 | 搬运前掉落或目标关节解释错误 | 恢复持物到投放点的顺序；统一标准 UR 六关节顺序；跨部件回归检查 |
| 将工具连接和对话存储当作同一系统 | SSH 已连接，但 Codex 不能接管另一 VSCode 终端；多机聊天不同步 | 单独验证执行位置、SSH 权限和对话归属；Git 负责项目同步，不用它假装实现聊天同步 |

## 规划成功、速度反复为 0：现在如何排查

现场现象由操作者确认：规划成功，机械臂完全不动，速度缩放反复为 0。完整原始 action 结果和运行状态目前缺失，所以根因仍待确认，不能只归因于“加入 ROS2”。

1. 使用独立 `project robot-check` 收集运行状态，避免与已有驱动重复启动。先记录程序是否运行、远程控制、安全状态、reverse 连接及 active 控制器，不先重复发送运动。
2. 分别核对 `speed_scaling` 和 `target_speed_fraction`。有效缩放是二者的乘积，任一为零都可能令轨迹停住。滑块升高不保证另一项变为正值。
3. 核对 headless 实际值及机器人控制程序状态。控制器 active 并不代表控制程序已运行或 reverse 链路可执行。
4. 运行条件正常后再进行现场认可的小范围动作，核对 action 返回与真实关节；保留原始值，才能判断到底是程序状态、滑块、安全停止、连接还是其他条件。

现有 headless 和时长适配保留。**不要绕过零速度检查，也不要把关闭名义时长监控视为问题已解决。**夹爪串口开合通过只证明夹爪通路可用。

## 本次重新组织时恢复与新增的解决办法

恢复 `harvesting_bringup`、配置和 `scripts/project`，适配现有 Foxy，不重新引入旧 Humble/Pixi 运行环境。根 README 原文保留，内部操作、测试设计和本复盘分别成文。

恢复有限次数采摘和公共请求处理，动作失败立即退出，不在持物期间自动复位或松爪。历史扫描数组按当前标准关节顺序重新排列；默认姿态仍未通过本次真机验收。单个检测点也执行距离过滤，避免“只有一个就直接接受”的例外。

默认 fake 隔离真实外设；robot/all 默认仅允许规划，gripper 默认拒绝写入；demo 同时要求运动开关和现场标定确认。统一构建产物和 Python 环境加载，去掉现场检查中重复激活环境与已不需要的 pyserial 前置要求。

当前工作站默认 Python 缺少 NumPy。使用已有的 torch 环境完成离线检查，未安装包或改动原环境；可通过 `HARVEST_CHECK_PYTHON` 显式指定。当前工作站没有 `/opt/ros/foxy`，因此本次没有执行 Foxy 编译、launch 集成或真机动作，这些必须按测试计划在现场补验。

## ROS2 的位置与价值

原作者项目已使用 ROS2 Humble 和 MoveIt；夹爪也原本通过 ROS 服务调用。ROS2 在本项目承担消息与服务、设备节点、坐标与启动编排；MoveIt 承担运动规划；UR 驱动和控制器承担执行链路，Robotiq SDK 承担串口设备通信。它们各自的成功条件不同。

在具身智能系统中，模型输出需要转换为可检查的设备请求，ROS2 提供常见的系统集成方式，但不是智能模型本身，也不是所有机器人任务的必要条件。单设备测试可以直接调用 SDK。对于当前包含相机、规划、机械臂与夹爪的项目，保留已有 ROS2 服务体系有实际价值；应先修好接口和运行状态，不凭“速度为零”就移除整个中间件。

## 跨电脑对话与 SSH 的未解决边界

Codex 的本地聊天、云端任务与 Work 对话不能假定共享同一份历史。个人账号的 Work Cloud 开放情况和实际设置尚未核实，也没有在本次开启任何同步开关；不能宣称它能迁移旧 Codex 对话。

SSH 连接成功不表示当前 Codex 会话自动拥有对另一 VSCode 集成终端的控制能力。应让执行端明确运行在远端，或通过获授权的 SSH 命令执行；不能把本地改代码误认为远端已构建/运行。本次修改范围是项目文档、结构、入口与离线验证，不声称解决桌面应用对话同步或接管已有终端。
